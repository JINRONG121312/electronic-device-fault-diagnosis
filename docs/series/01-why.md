# 一、为什么我要让电脑自己看病

> 本系列共 3 篇。本篇是第 1 篇，下一篇：[自机检测：让机器自己说清楚它怎么了](02-self-check.md)

## 一个熟悉的场景

笔记本蓝屏了。你抱到维修店，师傅看了一眼，说："内存的问题，换一根。"

换了，能开机。三天后又蓝屏。这回说"主板电容老化了，建议换主板"。

你开始怀疑：**他到底在看什么？**

后来我把那台机器的 `Minidump`、事件日志、驱动列表翻出来看，发现是一个第三方安全软件的驱动在系统更新后版本错配，每次触发网络过滤时踩栈溢出。删掉它，一年没再蓝屏。

这不是个例。很多被判定为"硬件故障"的问题，实际上是**驱动、系统、固件、配置或外部环境**的问题；而很多被当成"系统卡"的问题，又真的是硬盘快挂了。

问题是：**中间的归因这一层，常常被跳过了。**

## 我想要的不是"换哪个件"

市面上的诊断工具大多只做两件事：跑分、报错码。维修流程则从症状直接跳到换件。

这两者之间缺一个东西：**证据到归因的推理过程**。

所以我做的第一个决定是：把 FRU（Field Replaceable Unit，可更换模块）从"诊断结论"降级为"维修标签"。

```
错误做法：蓝屏 → 内存 → 换内存
我要的做法：蓝屏 → 证据 → 归因（驱动？OS？固件？边界？）→ 修复动作 or 换件
```

FRU 描述的是"怎么修"，不是"哪里坏"。把两者混在一起，就会得到"换了还是坏"的循环。

## 拆成五层

整个系统被拆成一条流水线，每一层只回答一个问题：

| 层 | 回答的问题 | 输出 |
|---|---|---|
| **证据采集** | 我们手上有哪些客观材料？ | 统一 Schema 的 `runtime_info.json` |
| **异常检测** | 这台机器现在正常吗？ | 健康度 + 异常项 |
| **故障分类** | 问题出在软件栈的哪一层？ | `driver_fault` / `os_fault` / `firmware_fault` / `configuration_fault` / `external_environment_fault` / `hardware_fault` / `mixed_or_uncertain` |
| **边界判断** | 证据更偏软件、偏硬件，还是卡在中间？ | `software_side` / `hardware_side` / `hardware_software_boundary` / `mixed_or_uncertain` |
| **故障决策** | 下一步该做什么？ | 软件修复 / 配置修复 / 固件处理 / 边界区分测试 / 硬件确认 / 继续补采 |

第三层和第四层是分开的，这点很重要。

同一台机器可以既是"驱动故障"（分类），又是"软硬件边界"（边界）——因为出问题的是驱动与硬件交互的那一段。**分类说"像什么"，边界说"能不能一锤定音"。**

## 为什么边界判断值得单列一层

软件和硬件不是两个盒子，它们是通过一条链子连起来的：

```
应用 → 系统调用 → 驱动 → 总线/固件 → 控制器 → 硬件
```

故障可以发生在链子的任何一段，而**大多数症状在链子两端看起来是一样的**：都表现为"设备不见了""卡住了""蓝屏了"。

所以真正有价值的结论不是"这是硬件问题"，而是：

> 证据在链子的这一段，你需要先做这个测试，才能区分是这一段的两侧哪一侧。

举例：硬盘读失败。
- SMART 里重映射扇区暴涨 → 偏硬件（`hardware_side`），可以直接建议换盘
- 只有 `storahci` 超时事件、SMART 干净 → 偏驱动/固件（`software_side`），先更新驱动
- 两者都有 → `hardware_software_boundary`，先跑一次短自检 + 换线材复测

**第三种情况如果直接换盘，钱就白花了。**

## 所以它是什么

一句话：**一个把"证据"翻译成"下一步动作"的原型**。
