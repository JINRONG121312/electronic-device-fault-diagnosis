# 三、互机诊断：用一台电脑给另一台看病

前两篇讲了"机器给自己体检"。但现实里更常见的情况是：**故障机自己跑不动程序了。**

这时候要换一个姿态——一台健康的机器当"诊断主机"，另一台当"被诊断机"。

## 三种模式，对应三种能力边界

| 模式 | 前提 | 系统能做什么 |
|---|---|---|
| **接口采集** | 故障机还能进系统，能起 Target Agent | 远程查询能力、下发采集、拉回证据、跑完整诊断 |
| **离线证据** | 不能稳定运行，但能导出 `runtime_info.json` | 用同一套诊断流程吃离线证据 |
| **现场指导** | 开不了机 / 反复蓝屏 / 盘读不出 | 只能给初步判断、补采清单、现场排查步骤 |

第三种最容易做错。

因为这时候系统手上几乎没有证据，只有用户口述的"开机没反应""风扇转但不亮"。**在这种信息量下给出确定性结论，等于算命。**

所以这一档的输出被刻意限制成：

- 记录哪些现象（电源灯、风扇、蜂鸣码、屏幕文字、外接屏结果）
- 建议做哪些交叉测试（换适配器、换插座、外接显示器、最小系统法）
- 明确写出"证据不足，无法区分 X 与 Y"

## 接口采集怎么跑

在被诊断机上起一个 Agent：

```powershell
python target_agent.py --host 0.0.0.0 --port 8790 --token lab-token
```

在诊断主机的"互机诊断"页填地址、Token、厂家型号、故障时间和症状描述，先"测试连接/查询能力"，确认这台机器**当前能采到哪几层证据**，再下采集任务。

这个"先查能力"的步骤很关键：

- 有些机器没装 `smartctl`，拿不到 SMART
- 有些机器事件日志权限不够，只能读到一部分
- 有些机器没有 dump，因为没开转储

**先知道能拿到什么，再决定诊断路径**——而不是先跑一套固定流程然后报错。

## 为什么用 Token，而不是"内网就随便连"

Target Agent 的设计里有个 `--token` 参数，看起来有点多余——毕竟大多数场景是同一个局域网。

但"能远程读一台机器的完整硬件清单和事件日志"，本身就是一个很敏感的能力。哪怕在内网，也不该默认任何人可连。

所以：绑定端口、要 Token、只暴露必要的采集接口，不提供任何写操作或 shell 执行。

这也是这个项目的一条底线：**诊断工具只读，不做任何修改。** 修不修、怎么修，由人决定。

## 真正的下一步：主动补采

这个项目里我自己最看重的部分，是"证据不足时该采什么"。

传统诊断工具的做法是：给一个结论，置信度 60%。用户不知道这 60% 是怎么来的，也不知道该做什么能提高到 90%。

这里换了个问法：

> 在现有证据下，做哪一个测试，能最大程度地区分剩下的几个候选？

这叫 Next-Best-Test。举个具体例子：

```
候选：driver_fault(0.4) / hardware_fault(0.35) / configuration_fault(0.25)

可做的测试：
  A. 更新存储驱动（成本 10 分钟，能区分 driver vs 其它）
  B. SSD 短自测     （成本 2 分钟，能区分 hardware vs 其它）
  C. 换线材         （成本 20 分钟 + 拆机，能区分接口 vs 其它）

系统推荐：先做 B（最便宜且切分最大），再做 A
```

它的价值不是"更准"，而是**把不确定性变成了可执行的动作**。

## 现在的边界

说几句实话：

- **权重是拍的。** 证据融合里的权重、NBT 的收益/成本参数，目前都是经验值，需要用真实维修案例（尤其是有 `repair_result` 回填的案例）来校准。
- **dump 只取元数据。** 没有集成 WinDbg `!analyze -v`，所以对"哪个驱动踩的栈"这种细粒度归因还做不到。
- **混合故障很难。** 同时存在两个独立故障时，系统倾向于输出 `mixed_or_uncertain`——这不算错，但也不够有用。
- **没有大规模验证。** 目前主要在公开数据集（RCAEval / LogHub / GAIA）和少量真实案例上跑过，跨机型泛化性还没验证。

## 这个系列想说的

三篇写下来，其实就一件事：

> **诊断的价值不在于给出答案，而在于把"不知道"变成"知道该问什么"。**

换件很容易。难的是在换之前，搞清楚到底该不该换。
