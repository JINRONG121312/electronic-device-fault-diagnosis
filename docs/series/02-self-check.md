# 二、自机检测：让机器自己说清楚它怎么了

> 本系列共 3 篇。本篇是第 2 篇，上一篇：[为什么我要让电脑自己看病](01-why.md)，下一篇：[互机诊断：用一台电脑给另一台看病](03-remote.md)

上一篇说到，整套系统被拆成五层：证据采集 → 异常检测 → 故障分类 → 边界判断 → 故障决策。

这一篇讲第一层和第二层：**证据从哪来，机器怎么给自己体检。**

## 证据分六层，不是一堆日志

很多人做诊断，第一步就是"抓日志"。但日志只是证据的一种，而且往往是最脏的一种。

我把证据分成六层，统一进一个 Schema：

| 层 | 内容 | 典型来源 |
|---|---|---|
| `inventory` | 厂家、型号、序列号、OS、BIOS、PnP 设备、PCI/USB/块设备 | WMI、`Get-PnpDevice`、`lsblk` |
| `logs` | 系统/应用事件、Reliability、journalctl、dmesg | Event Log、Syslog |
| `metrics` | SMART/NVMe、电池、电源、内存、温度、网络、存储延迟 | `smartctl`、`powercfg /batteryreport` |
| `active_tests` | 网关 ping、外接屏、适配器交叉测试、短自测 | 主动发起 |
| `crash_dump` | BugCheck、minidump / MEMORY.DMP 元数据、WHEA、Kernel-Power | `C:\Windows\Minidump` |
| `repair_result` | 维修动作、是否解决、最终根因 | 人工回填 |

前五层是"机器能说的"，最后一层是"人补上的"。

`repair_result` 看着最不重要，其实对研究最关键——**没有它，就没法算准确率、没法算"不必要换件率"**。一个诊断系统如果永远不知道自己对不对，它就只是个话术生成器。

## 自机检测的三步

适用于：本机操作系统还能跑程序（哪怕很卡）。

```
1. 扫描本机   → 生成设备画像（机型 / OS / 该采哪些项）
2. 采集数据   → 写出 runtime_info.json
3. 开始诊断   → 健康度 + 分类 + 边界 + 决策
```

第三步如果提示"证据不足"，页面会给一张**补采清单**，告诉你还差什么。这是刻意的设计：**系统允许自己不知道。**

## 蓝屏为什么要拆成四种情况

蓝屏是最常见的求助场景，也是最容易被做错的地方。

一个"诊断蓝屏"的功能，实际上是四种完全不同的工况：

| 情况 | 前提 | 能拿到什么 |
|---|---|---|
| **① 自机重启后诊断** | 已经重启，程序能跑 | Minidump、MEMORY.DMP 元数据、BugCheck、WHEA、Kernel-Power、近期驱动更新、SMART |
| **② 互机接口采集** | 故障机还能进系统，能跑 Agent | 同上，但由另一台机器远程拉取 |
| **③ 离线证据导入** | 不能稳定运行，但硬盘可读 | 从 WinPE / 安全模式 / 拆盘复制出来的 dump 与事件日志 |
| **④ 无法交互** | 开不了机、反复蓝屏、硬盘读不出 | 只有照片、stop code、时间、最近变更 |

**这四种情况下，系统的输出应该完全不同。**

第 ④ 种如果还硬要输出"硬件故障，建议更换主板"，那是在骗人——它手上只有一个 stop code 的照片。所以这一档只输出：初步判断 + 现场排查步骤 + 该补哪些证据。

## dump 是证据，不是模块

一个容易走偏的设计是把"蓝屏分析"做成独立模块。我没有这么做。

因为蓝屏是**症状**（symptom），不是故障类型。dump 是**证据**（evidence），不是诊断器。

```
蓝屏（症状）
  → crash_dump（证据层）
  → 故障分类（可能是 driver_fault）
  → 边界判断（可能是 boundary）
  → 决策（先更新驱动 / 先跑内存测试）
```

这个抽象带来的好处是：**同一个诊断流程，可以吃蓝屏、黑屏、无法充电、无法联网**——它们只是不同的症状入口，进来以后走同一条流水线。

如果 dump 拿不到，系统不会静默失败，而是明确写：

```json
{
  "available": false,
  "reason": "dump_not_found_or_machine_unavailable",
  "next_action": "enable_dump_or_collect_offline_evidence"
}
```

**"没有证据"本身也是一条证据。** 它告诉决策层：这里的信息缺口需要先补上，而不是猜。

## 一个具体的例子

假设一台机器报"随机蓝屏"，自机检测的结果是：

```
健康度：62（异常）
异常项：Kernel-Power 41 多次、storahci 超时 3 次
分类：driver_fault
边界：hardware_software_boundary
决策：先更新存储控制器驱动 → 复测 72 小时 → 仍复现则换线材 + 跑 SSD 短自测
```

注意它没有说"换硬盘"。

因为它手上同时有两类证据：一类指向驱动（超时事件），一类指向硬件（Kernel-Power 掉电）。这时候正确的动作是**做一个能区分两者的测试**，而不是赌一个。

这就是上一篇说的：**分类说"像什么"，边界说"能不能一锤定音"。**
