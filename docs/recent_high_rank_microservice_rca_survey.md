# 2022-2026 高水平微服务多源故障诊断与根因定位文献调研

调研日期：2026-07-13。

## 1. 检索与筛选标准

检索来源包括 Crossref、OpenAlex、DBLP、出版社 DOI 元数据、论文摘要和公开代码仓库。关键词覆盖：

- `microservice root cause analysis`
- `microservice failure diagnosis multimodal data`
- `logs metrics traces root cause localization`
- `multi-source observability microservice troubleshooting`
- `causal discovery microservice RCA`

纳入条件：2022-2026 年正式发表；研究对象为微服务或在线服务系统；任务包含根因定位、故障类型识别或故障诊断；会议为 CCF A/B 或公认高水平会议，期刊原则上为 JCR Q1/Q2 或 CCF A/B。

会议论文没有 JCR 分区，因此采用 CCF 等级和领域认可度。期刊分区会随年份和学科类别变化，最终论文中的“一区/二区”表述应以学校可访问的当年 JCR 数据复核。

## 3. 论文应采用的基线组合

### 第一优先级：主要多模态强基线

1. **TVDiag**：目前最接近本项目的最新方法，必须优先复现。
2. **Medicine**：直接研究模态贡献不平衡，是检验可靠性加权和分层融合的关键对照。
3. **DiagFusion**：同时输出根因实例和故障类型，与当前任务完全对齐。
4. **FAMOS**：ICSE 2025 的跨模态注意力方法，代表较新的深度融合路线。
5. **Eadro**：端到端检测与定位的经典多源强基线。

### 第二优先级：方法机制对照

1. **MRCA**：验证“异常服务筛选 + 指标因果图”是否优于当前联合重排。
2. **RUN**：提供纯指标、神经因果发现对照。
3. **Nezha**：提供事件图和可解释细粒度对照。
4. **TORAI**：用于缺失调用链、黑盒服务或模态缺失的鲁棒性实验。
5. **BARO**：保留为指标单模态强基线，但不应作为唯一主要文献基线。

CloudRanger、TraceRCA 和简单 TF-IDF 可以保留在附录或 sanity-check 表中，但不应再占据主结果表的核心位置。

## 3.1 不纳入主要基线的近期工作

- 仅发布在 arXiv、Preprints.org 或尚未确认正式录用的 2025-2026 LLM/多智能体 RCA 方法，不满足“二区以上正式论文”的筛选条件。
- 只做异常检测、不输出根因服务或故障类型的方法，不与本项目的主任务直接对比。
- 面向安全攻击溯源、网络告警压缩、工业传感器故障诊断而非微服务可观测数据的方法，即使期刊分区较高，也不纳入基线。
- RCAEval 属于基准论文，不是待比较的新诊断算法；其推荐列表只能帮助复现，不能替代独立文献筛选。

## 4. 基于现有 RE2 数据的可复现性判断

现有 RE2 数据包含指标 CSV、日志 CSV、调用链 CSV，以及服务和故障类型标签，理论上支持 TVDiag、Medicine、DiagFusion、Eadro、Nezha、MRCA 和 FAMOS 的任务定义。

当前障碍不是标签不足，而是规范化案例中的日志和调用链主要保存为聚合表示。复现上述方法时应直接读取 `metadata.source_files` 指向的原始 CSV，重新构建：

- 服务时间窗级指标异常序列；
- 日志模板/事件序列及其时间分布；
- span 或调用边时间序列；
- 服务部署图和调用依赖图；
- 每个案例的多模态图样本。

不能继续使用当前聚合统计去声称“复现了 TVDiag/DiagFusion/FAMOS”，否则模型输入与原论文不一致。

## 5. 推荐复现顺序

1. **TVDiag**：官方仓库完整，任务匹配度最高；先完成数据适配与官方样例复跑。
2. **Medicine**：官方仓库可用，重点复现模态独立编码和动态优化。
3. **Nezha**：官方仓库可用，可作为非神经联合事件图方法。
4. **RUN**：官方代码简单，建立因果发现强基线。
5. **TORAI**：官方代码和数据均公开，作为 2026 年最新鲁棒性基线。
6. **DiagFusion/Eadro/FAMOS/MRCA/UniDiag**：若找不到稳定代码，联系作者或按论文模块进行受控再实现，并明确标注 reproduction 与 reimplementation 的区别。

## 7. 对当前研究问题的启示

近三年的研究重点已经从“是否融合多模态”转向：

1. 模态对不同诊断任务的贡献是否应区别建模（TVDiag）；
2. 强模态是否压制弱模态（Medicine）；
3. 跨模态关系是否在图或注意力层面深度建模（FAMOS、UniDiag）；
4. 是否能够输出服务以下的指标、代码区域或资源类型根因（MRCA、Nezha）；
5. 模态缺失和调用图盲点下是否仍能诊断（TORAI）。

因此，当前论文不能只把贡献写成“联合服务与故障类型排序”。更有竞争力的问题应调整为：

> 面向未见服务-故障组合与模态质量不均衡场景，如何学习任务相关的跨模态联合表示，并保持可解释的组合根因排序？

这个问题能够与 TVDiag 的任务导向建模、Medicine 的模态平衡、FAMOS 的跨模态注意力和 TORAI 的缺失观测鲁棒性形成直接对话。
